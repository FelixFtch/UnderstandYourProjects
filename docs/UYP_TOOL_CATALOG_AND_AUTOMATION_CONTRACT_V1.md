# UYP Tool Catalog and Automation Contract V1

**Status:** design contract (2026-10-13)  
**Owner:** UnderstandYourProjects (UYP) for the knowledge-plane sections; HomeHub owns the control-plane sections.

This contract makes the Jetson Agent Box discoverable without turning UYP into a
second HomeHub. It defines the boundary between project knowledge tools,
Home Assistant capability projections, and scheduled automations. It is a
contract for the next implementation slice; it does not claim that any of the
routes below are deployed.

## 1. Authority and data flow

HomeHub remains the only authority for identity, device ownership, pairing,
grants, policy, revocation, automation ownership, and audit. UYP owns project
discovery, indexing, Understand Anything graphs, retrieval, evidence, and
IndexJob state. Home Assistant is a device gateway behind HomeHub. A browser,
phone, or Jetson must not call Home Assistant directly.

```text
iPhone / Studio
    -> HomeHub BFF (identity, policy, tool admission, automation)
        -> HomeHub tool dispatcher
            -> curated Home Assistant adapter (device actions)
            -> UYP tool adapter (project knowledge / IndexJob)
        <- HomeHub audit and state confirmation

Jetson Agent Box
    <- HomeHub-scoped tool catalog + device capability projection
    -> UYP local worker (IndexJob and evidence)
    -> HomeHub events (project.sync / index.completed)
```

The Jetson may cache a catalog for offline display, but a cached descriptor is
not an authorization. Every invocation re-checks the HomeHub session/grant
epoch (or fails closed). UYP never mints a grant, chooses a device owner, or
records an HA token.

## 2. Tool descriptors

Studio, the phone app, and Jetson tools should consume one normalized descriptor
shape. HomeHub supplies the complete catalog and filters it by the caller's
AccessContext. UYP supplies only the project-knowledge descriptors listed in
§2.2.

```json
{
  "toolId": "project.sync",
  "version": "1.0",
  "displayName": "Sync project knowledge",
  "description": "Queue a scoped incremental Understand Anything run.",
  "owner": "uyp",
  "kind": "knowledge",
  "operation": "command",
  "requiredScopes": ["project:alpha", "source:connector:mac"],
  "confirmation": "owner_or_policy",
  "idempotency": "required",
  "freshness": {"maxAgeSeconds": 300},
  "inputSchema": {"type": "object", "required": ["projectId"]},
  "resultSchema": {"$ref": "#/schemas/IndexJobAccepted"},
  "availability": {"state": "current", "checkedAt": "2026-10-13T22:21:11Z"}
}
```

The descriptor is intentionally a capability description, not an executable
URL. URLs, bearer tokens, HA service names, and raw filesystem paths are never
returned to the browser or persisted in the catalog. `requiredScopes` are
opaque HomeHub capability identifiers; UYP only compares them with the
validated AccessContext it receives.

### 2.1 Canonical fields

| Field | Rule |
| --- | --- |
| `toolId` | Stable lower-case dotted name. It is the dispatch key and is never generated by an LLM. |
| `version` | Semver-like contract version. A breaking parameter/result change increments the major component. |
| `displayName` | Human-readable localization key or bounded label. HomeHub may localize it. |
| `owner` | `homehub`, `uyp`, or another approved adapter. The owner is responsible for implementation and audit. |
| `kind` | `knowledge`, `home`, `communication`, or `system`. UYP exposes only `knowledge`. |
| `operation` | `query` or `command`. UYP project reads are queries; `project.sync` is a command. |
| `requiredScopes` | Opaque project/source/device scope IDs. No paths, tokens, or entity IDs. |
| `confirmation` | `none`, `owner_or_policy`, or `explicit_owner`. Writes and device actions default to explicit confirmation. |
| `idempotency` | `none`, `optional`, or `required`. Commands that queue work use `required`. |
| `freshness` | Maximum acceptable age for the capability projection, not a promise that data is fresh. |
| `inputSchema` / `resultSchema` | Bounded JSON Schema; reject unknown high-risk fields and excessive strings/arrays. |
| `availability` | Current projection state (`current`, `partial`, `offline`, `revoked`, `unsupported`) plus check time. |

### 2.2 UYP-owned project tools

These are the only tools UYP may advertise in the initial catalog:

| Tool | Operation | Scope | Effect |
| --- | --- | --- | --- |
| `project.list` | query | project metadata | Return caller-scoped projects and freshness. |
| `project.status` | query | one project | Return digest, IndexJob phase, and knowledge version. |
| `project.ask` | query | project/source | Search local knowledge and return evidence-backed text. |
| `project.related` | query | project | Return bounded graph relationships and reusable candidates. |
| `source.locate` | query | source/project | Locate a symbol or file in indexed evidence. |
| `source.read_evidence` | query | source/project | Return bounded indexed evidence; never arbitrary live-file bytes. |
| `index.status` | query | project/source | Return queue, worker, and freshness state. |
| `project.sync` | command | owner plus project/source | Create or resume a durable IndexJob after HomeHub approval. |

`project.sync` accepts an opaque `projectId` and approved `sourceId`, not an
arbitrary `path`. The existing `POST /api/projects/analyze {path,device_id}`
route remains a Studio compatibility route while it is migrated: the HomeHub
proxy resolves the selected folder to a project/source capability first, then
passes only those IDs to UYP. A path that is not already approved must return
`source_approval_required`, not trigger a Connector read.

## 3. Home Assistant capability projection

Home Assistant has a large and useful domain/service vocabulary, but exposing
it directly would bypass HomeHub policy and make every HA integration a custom
case. HomeHub should publish a small, normalized projection. UYP may consume
the projection for context or project automation results, but does not control
HA.

The projection is read-only and contains stable HomeHub identifiers:

```json
{
  "homeDeviceId": "home-device-living-room-light",
  "displayName": "Living room lamp",
  "roomId": "living_room",
  "domain": "light",
  "state": "on",
  "availability": "online",
  "lastSeenAt": "2026-10-13T22:20:58Z",
  "capabilities": ["home.light.read", "home.light.turn_on", "home.light.turn_off"],
  "source": {"kind": "home_assistant", "uniqueId": "opaque-ha-unique-id"},
  "projectionEpoch": "ha-epoch-17"
}
```

`homeDeviceId`, `roomId`, and `capabilities` are HomeHub identifiers. The
projection must not include HA access tokens, credentials, arbitrary service
names, local IP addresses, MQTT topics, camera bytes, or full recorder history.
`source.uniqueId` is optional and may be redacted from untrusted members.

### 3.1 Canonical HomeHub tool names

HomeHub maps repeated HA operations to a small canonical set:

```text
home.device.list             query
home.device.read_state       query
home.light.turn_on           command
home.light.turn_off          command
home.light.set_brightness    command
home.sensor.read             query
home.automation.list         query
home.automation.enable       command (owner confirmation)
home.automation.disable      command (owner confirmation)
```

The first write milestone should expose only `home.light.turn_on` and
`home.light.turn_off` for one explicitly approved lamp. `set_brightness`,
scenes, media, and presence rules follow state-confirmation tests. An unmapped
HA domain remains read-only and is omitted from the command catalog.

### 3.2 Automatic naming and aliases

Names are deterministic and HomeHub-owned:

```text
canonical tool: home.light.turn_off
device identity: home-device-<stable-id>
display label: <HomeHub room label> + <device label>
```

For example, the currently documented Govee H60B0 may be displayed as
`Living room lamp`, while its stable `homeDeviceId` remains unchanged when its
IP changes. An alias such as `客厅灯` or `living room light` is a UI/search
synonym and never an authorization key. If two devices share a label, Studio
must show the room and a disambiguating suffix; it must not silently choose one.

The Jetson may generate a provisional display label for an unregistered device,
but it must mark it `pending_homehub_name` and cannot invoke a command until
HomeHub registers the device and returns the stable ID.

## 4. Catalog and device discovery interfaces

These are the proposed versioned interfaces. They can be served by HomeHub's
Studio BFF and consumed by the phone, Studio, and Jetson:

```text
GET  /api/studio/tool-catalog
GET  /api/studio/home-devices
GET  /api/studio/home-devices/{homeDeviceId}
GET  /api/studio/automations
POST /api/studio/automations
PATCH /api/studio/automations/{automationId}
GET  /api/studio/automations/{automationId}/runs
```

The caller's HomeHub bearer determines the returned catalog. The Jetson's
service-to-service adapter may use a short-lived HomeHub service credential,
but must receive the same filtered shape and `catalogEpoch`; it must not read
the HomeHub database. A local UYP projection may expose:

```text
GET /api/tools/catalog       # UYP-owned project tools only; loopback/service auth
GET /api/tools/health        # catalog epoch, UYP worker and connector freshness
```

These UYP routes describe callable project tools and worker state. They do not
create HomeHub tools, grant device access, or expose HA entities. Until the
HomeHub BFF routes exist, Studio must label these states `contract_pending`
rather than presenting a fake pairing or automation control.

## 5. Event contract: project sync and indexing

HomeHub automation emits a `project.sync.requested` event after policy and
source approval. UYP owns the durable IndexJob and emits completion/failure
events. Events are append-only, idempotent, and safe to retry.

### 5.1 Common envelope

```json
{
  "schema": "uyp.event.v1",
  "eventId": "evt_01J...",
  "eventType": "project.sync.requested",
  "occurredAt": "2026-10-13T22:21:11Z",
  "producer": {"kind": "homehub", "nodeId": "hub_..."},
  "principal": {"memberId": "felix", "sessionId": "session_..."},
  "grantEpoch": "27",
  "idempotencyKey": "sync:project-alpha:source-mac:2026-10-13",
  "payload": {}
}
```

`sessionId` and `grantEpoch` are references for validation/audit. A token is
never embedded in an event. UYP records only the minimum principal projection
needed for policy checks. Event consumers must reject an expired/revoked epoch
and safely acknowledge duplicate `eventId` or `idempotencyKey` values.

### 5.2 `project.sync.requested`

```json
{
  "schema": "uyp.event.v1",
  "eventType": "project.sync.requested",
  "payload": {
    "projectId": "project:alpha",
    "sourceId": "connector:mac",
    "requestedMode": "incremental",
    "requestedBy": "automation:daily-project-sync",
    "connectorGrantRef": "g_opaque",
    "sourceEpoch": "source-epoch-42",
    "priority": "background",
    "dryRun": false
  }
}
```

The event must not include `path`, `endpoint`, connector token, or source
bytes. `connectorGrantRef` is opaque and is resolved by the Connector adapter;
it is not interchangeable with a HomeHub grant. UYP responds with
`index.accepted` or `index.rejected` and stores the event ID on the IndexJob.

### 5.3 `index.completed`

```json
{
  "schema": "uyp.event.v1",
  "eventType": "index.completed",
  "payload": {
    "indexJobId": "job_01J...",
    "projectId": "project:alpha",
    "sourceId": "connector:mac",
    "sourceEpoch": "source-epoch-43",
    "knowledgeVersion": "kv_2026-10-13T22:22:10Z",
    "phase": "published",
    "counts": {"discovered": 120, "indexed": 118, "deleted": 2, "failed": 0},
    "graph": {"nodes": 751, "edges": 946, "layers": 4, "tourSteps": 12},
    "freshness": {"state": "current", "indexedAt": "2026-10-13T22:22:10Z"},
    "evidenceRefs": ["evidence:project-alpha:kv_..."],
    "warnings": []
  }
}
```

`index.completed` is a knowledge result, not an automation permission. HomeHub
may use it to produce a digest or notify the owner, but it must re-check the
recipient's policy before revealing project names, paths, or evidence. The
event may contain bounded counts and opaque evidence references; it must never
contain full source text or a raw graph database.

### 5.4 Failure and revocation events

UYP emits `index.failed` with `reason` from the bounded enum
`connector_unavailable`, `source_changed`, `parse_error`, `model_unavailable`,
`access_context_unavailable`, `revoked`, or `resource_limit`. It emits
`index.revoked` when a running job stops because HomeHub advanced the grant
epoch. A retryable failure includes `retryAt` and `attempt`; neither event
silently reports a successful stale version.

## 6. Automation handoff

HomeHub owns automation CRUD, trigger evaluation, command confirmation, device
leases, and audit. UYP owns only the `project.sync` command implementation and
IndexJob events. A scheduled project digest is therefore two explicit steps:

```text
HomeHub automation schedule
  -> policy/owner/revocation check
  -> project.sync.requested
  -> UYP durable IndexJob
  -> index.completed / index.failed
  -> HomeHub digest/notification policy check
```

UYP does not import Home Assistant's YAML automation engine and does not call
HA service endpoints. HomeHub may model a trigger as a canonical tool call,
for example `home.light.turn_off` or `project.sync`, and persist its own
automation record:

```json
{
  "automationId": "automation:daily-project-sync",
  "trigger": {"kind": "cron", "expression": "0 9 * * *", "timezone": "America/New_York"},
  "action": {"toolId": "project.sync", "args": {"projectId": "project:alpha"}},
  "enabled": true,
  "requiresConfirmation": false,
  "ownerMemberId": "felix"
}
```

Device writes such as `home.light.turn_off` require explicit HomeHub policy,
stable device IDs, an availability/freshness check, resource lease and state
confirmation. A UYP project-sync job never inherits permission to control a
home device merely because both actions run on the same Jetson.

## 7. Jetson discovery and readiness

At startup, the Jetson worker should request a filtered catalog and device
projection, then record only this non-sensitive cache under its own state root:

```json
{
  "catalogEpoch": "homehub-catalog-17",
  "grantEpoch": "27",
  "checkedAt": "2026-10-13T22:21:11Z",
  "tools": ["project.list", "project.ask", "project.sync"],
  "homeDeviceIds": ["home-device-living-room-light"],
  "state": "current"
}
```

The cache is invalidated when its TTL, `grantEpoch`, `catalogEpoch`, or device
projection epoch changes. `current` means the projection was validated; it
does not mean every source or device is online. A Jetson that has no valid
catalog must continue serving only local health diagnostics and must reject
commands with `tool_catalog_unavailable`.

## 8. Implementation and conformance checklist

Before the next production claim, add offline contract tests for:

1. `project.sync.requested` creates one durable IndexJob for one idempotency key.
2. Duplicate event delivery returns the original job and does not enqueue a
   second deep analysis.
3. Connector capability IDs and HomeHub grant IDs cannot be substituted for
   one another.
4. Expired/revoked `grantEpoch` produces `index.revoked` and no evidence leak.
5. `index.completed` contains bounded counts and evidence references but no
   paths, source bytes, credentials, or raw graph payload.
6. A catalog filtered for a guest contains no `project.sync` or device command.
7. A stale device projection cannot invoke `home.light.*`.
8. Tool display names are deterministic and duplicate labels are disambiguated.
9. A missing HomeHub catalog is shown as `contract_pending`/`unavailable`, not
   as an enabled button.

This contract leaves physical device control, HomeHub automation routes, and
the HA adapter implementation in the HomeHub repository. UYP can implement
the event validator, IndexJob idempotency handling, and project tool catalog
without changing the protected voice runtime.
